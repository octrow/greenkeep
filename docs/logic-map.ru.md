# Карта логики

Как один прогон greenkeep превращает опекаемые репо в смёрженные fix PR и дайджест в Telegram.
Карта описывает код как он есть сейчас, шаг за шагом.
У каждого шага: что он решает, где поток ветвится и какой модуль это делает.

Это зеркало `docs/logic-map.md`; источник истины — английский файл. Правится в том же коммите.
Термины — в `CONTEXT.md`. Известные пробелы и исправления — в `PLAN.md`.
`tests/test_logic_map.py` проверяет, что каждая строка `Module:` указывает на настоящий модуль.

## Поток одним взглядом

```
systemd-таймер (каждый час) / CLI / кнопка дашборда
  │
  ├─ 1  Пауза .............. есть ли ~/.config/greenkeep/PAUSE?
  ├─ 2  Раз в день ......... плановый прогон сегодня уже был (в буст не важно)?
  ├─ 3  Уборка ............. какие старые клоны старше суток?
  ├─ 4  Цели ............... какие репо, какой бюджет, идёт ли буст?
  ├─ 5  Опции .............. какая модель пишет, ревьюит и планирует?
  ├─ 6  Порядок репо ....... сначала Focus, потом давно не сливавшиеся
  │   по каждому репо:
  ├─ 7  Cool-down .......... отдыхает ли репо после двух парковок? → только уязвимости и Dependabot
  ├─ 8  Клон ............... свежий клон; буст добавляет правила ruff
  ├─ 9  Откаты ............. откатил ли владелец слияние greenkeep? → автопауза
  ├─ 10 Базовые тесты ...... зелёный ли набор в чистом клоне и что он покрывает?
  ├─ 11 Находки ............ ruff, покрытие, pip-audit, устаревшие, готовность
  ├─ 12 Заметки владельцу .. что решает только владелец (лицензия, README)
  ├─ 13 Порядок работы ..... безопасность, баги lint, тесты, обновления, готовность, стиль
  ├─ 14 Кандидаты .......... рабочие, не vendored, посильные; первые 10
  ├─ 15 Охота на баги ...... только когда кандидатов нет
  │   по каждому кандидату, пока один не сольётся:
  ├─ 16 Бюджет ............. пускает ли дневной бюджет?
  ├─ 17 Issue плана ........ один issue на находку (только push)
  ├─ 18 Изменение .......... ruff --fix, uv lock, шаблон или Claude (с планом Opus)
  ├─ 19 Гейт ............... рамки, без подавлений, без нового lint, тесты, проверка вида
  ├─ 20 Ревью .............. Opus читает diff в клоне (только изменения LLM)
  ├─ 21 Посадка ............ коммит, push, PR, squash-merge
  ├─ 22 Провал ............. засчитать попытку, запарковать, заморозить репо
  │   после своей работы в репо:
  ├─ 23 Dependabot ......... слить его PR в пределах мажора на зелёных локальных тестах
  │
  ├─ 24 Остановки прогона .. автопауза, Claude недоступен, сломанное репо
  └─ 25 Дайджест ........... текст в Telegram; отметить день
  │
смёржённые PR, issue, state.db, дайджест
```

Дашборд (`greenkeep-ui`) в основной поток не входит: читает state.db и лог, удаляет PAUSE, запускает dry run.

## Где поток делится по виду находки

Большую часть решает один реестр: `kinds.KINDS` сопоставляет `Finding.kind` и `Kind` с приоритетом, изготовлением, рамками и пост-проверками.
Несколько развилок живут вне реестра: префиксы кода правила и префиксы отпечатка.

| Вид / вариант | Включается | Шаги | Что меняется |
|---|---|---|---|
| `vuln` | pip-audit нашёл исправление для каждой advisory | 13, 16, 18, 19, 22 | первым; вне бюджета; `uv lock --upgrade-package`; меняется только `uv.lock`; паркуется с первого провала |
| `outdated` | `uv tree --outdated`, нет Dependabot для uv/pip | 11, 13, 14, 18, 22 | после тестов; тратит бюджет; пропуск при покрытии ниже 60%; `uv lock`; паркуется с первого провала |
| `ruff` S/F/B (ранг ≤ 2) | буквенный префикс правила | 13, 21 | как баги; коммит `fix` |
| `ruff` прочие | префикс правила | 13 | стиль, последними; коммит `chore` |
| `ruff` с безопасным фиксом | `fix.applicability == "safe"` | 18, 20 | `ruff --fix`, без LLM и ревью |
| `ruff` C901/PLR0912/PLR0915 | `kinds.HARD_RULES` | 18 | в буст сначала план Opus |
| `untested` | модуль покрыт < 50%, ≥ 5 операторов | 14, 18, 19 | только новый тестовый файл в пределах бюджета строк; покрытие должно вырасти; в буст план Opus |
| `ready` | провал проверки готовности | 18, 19 | шаблон для readme-field/urls/ci-badge, Claude для текста; один файл, одно поле `[project]` |
| `bug` | охота (шаг 15) | 14, 18, 19 | минует шаг 14; фикс исходника и добавленный тест, падающий без фикса; в буст план Opus |
| буст | `boost_until` в будущем | 2, 4, 5, 8, 15 | прогоны каждый час, бюджет 15, доп. правила ruff, `hunt` во всех репо, планировщик Opus |

Примеры:
- `F401` на покрытой строке → шаг 18 `ruff --fix`, без ревью; коммит `fix: F401: …`, PR `F401: …`.
- `SIM103` в буст → патч Claude, гейт, ревью Opus; изменённая строка, которую тесты не выполняли, валит гейт.
- `vuln:certifi:PYSEC-…` при исчерпанном бюджете → всё равно работается и сливается, не считается.

Освобождение от бюджета читается дважды: `Kind.exempt_from_budget` и `state.BUDGET_FREE` (`vuln:`) в `State.merged_today`; `state` не может импортировать `kinds`, их равенство держит тест.

Module: `kinds`, `findings`, `state`

## Точки входа

Все вызывают `cli.main`. Различаются умолчаниями.

| Вход | Репо | Push | Бюджет | Буст | Заметки |
|---|---|---|---|---|---|
| systemd `greenkeep.service`, таймер каждый час | конфиг | да | конфиг (по умолчанию 3, выходные 1, буст 15) | из конфига | `greenkeep --push`: плановый прогон |
| CLI `greenkeep --push` | конфиг | да | конфиг | из конфига | тоже плановый: защита «раз в день», `record_run` |
| CLI `greenkeep` | конфиг | нет (dry run) | конфиг | из конфига | см. «Dry run» ниже |
| CLI `greenkeep owner/name …` | названные; запись конфига, если есть | флаг | `--budget` или из конфига; **3**, если конфиг не читается | из конфига, если читается | без защиты «раз в день»; в push сегодняшние слияния всех репо идут в счёт бюджета |
| кнопка дашборда «Dry run now» | конфиг | нет | конфиг | из конфига | `uv run --project <checkout> greenkeep`; при PAUSE ничего не делает |
| кнопка дашборда «Run with options…» | диалог (пусто: конфиг) | переключатель (push сначала просит подтверждение) | диалог (пусто: конфиг) | диалог (дефолты CLI подставлены) | та же команда с флагами CLI; `--keep` — чекбокс |

Dry run: состояние в памяти, поэтому нет слияний, попыток, cool-down, меток охоты и откатов, и он может «слить» весь бюджет независимо от реального дня.
Он всё равно тратит подписку (патчер, планировщик, ревью, охота), убирает старые клоны, клонирует и синхронизирует, ходит в PyPI, pip-audit и `gh pr list`, пишет в общий лог.

`--model` (по умолчанию `claude-sonnet-5-5`) пишет патчи, тексты README и description, охотится; `--review-model` (по умолчанию `claude-opus-5-5`) ревьюит, сомневается в находках охоты и в буст планирует.
Каждый вызов Claude — прямой `claude -p` (без OmniRoute), только `Read,Grep,Glob`, без пользовательских настроек: платит аккаунт, под которым залогинен Claude Code.

Module: `cli`, `ui`, `config`

## Шаги

### 1. Пауза

Решает: делает ли прогон хоть что-то.
Ветки: `~/.config/greenkeep/PAUSE` есть → лог «paused», выход 0, без дайджеста; нет → дальше.
Файл пишет шаг 24 (автопауза), удаляет владелец или дашборд.
Module: `cli`, `config`

### 2. Раз в день

Решает: сделал ли плановый прогон сегодняшнюю работу.
Ветки:
- плановый (`--push`, репо не названы), метка `run` = сегодня, буста нет → выход 0;
- буст → каждый час;
- названные репо или dry run → никогда не пропускаются.
Метка хранит дату начала прогона, ту же, что проверяет защита.
Сбой: сломанный конфиг при проверке буста → буста нет.
Module: `cli`, `state`

### 3. Уборка

Решает: какие клоны в `~/.cache/greenkeep/run-*` остались от убитого прогона.
Ветки: mtime старше 24 ч → удалить; остальные не трогать. Работает и в dry run.
Module: `workspace`

### 4. Цели

Решает: список репо и дневной бюджет слияний.
Вход: argv, `config.toml`. Выход: `list[Target]`, бюджет.
Ветки:
- названы репо → они, с записью конфига (корень тестов, hunt), если есть; бюджет `--budget`, иначе `budget_at(now)` из конфига, иначе 3, если конфиг не читается;
- не названы → `repos` из конфига; бюджет `--budget` или `budget_at(now)`;
- буст (`now < boost_until`, и для названных репо, если конфиг читается) → у всех `hunt=True, boost=True`; бюджет `boost_budget` (15);
- суббота и воскресенье → `weekend_budget` (1); иначе `budget` (3).
Сбой: нет или сломан конфиг без названных репо (с названными он игнорируется) → `ConfigError`, exit 1; push → дайджест в одну строку раз в день (метка `config-error`); `boost_until` без смещения — ошибка конфига.
Module: `cli`, `config`

### 5. Опции

Решает: какая модель пишет, ревьюит и планирует.
Ветки: буст → `planner = review_model` (Opus планирует трудные изменения, шаг 18); иначе планировщика нет.
Буст здесь читается из конфига заново, и для названных репо тоже.
Module: `cli`, `core`

### 6. Порядок репо

Решает: какие репо первыми получают бюджет.
Порядок: Focus, затем по `last_merge` по возрастанию (никогда не сливавшиеся первыми).
Исчерпанный бюджет не мешает обойти все репо: уязвимостям и Dependabot он не нужен.
Репо в cool-down всё равно получает фиксы уязвимостей и слияния Dependabot (шаг 7).
Module: `cli`, `state`

### 7. Cool-down

Решает: полный прогон репо или только то, что не может ждать.
Ветки:
- метки нет → работать;
- `today < until`, HEAD origin не изменился (или недоступен), HEAD greenkeep не изменился → «in cool-down», но клон всё равно: только находки вне бюджета (`vuln`), без охоты, затем Dependabot (шаг 23);
- иначе → снять метку, работать.
Цена: один `git ls-remote` на каждое замороженное репо, плюс клон, sync и базовые тесты.
Module: `run`, `state`, `workspace`

### 8. Клон

Решает: одноразовое рабочее место, которое прогон может менять.
Вход: `Target`. Выход: `Workspace`.
Ветки:
- локальный checkout → его `origin`, `--reference-if-able` на checkout, копия `.env`;
- `owner/name` → `https://github.com/owner/name.git`;
- буст → `extra_rules` = C901, PLR0912, PLR0915, SIM, PERF, UP, RUF (без RUF001-003, RUF100) во всех вызовах ruff в этом репо, включая проверку нового lint, кроме файлов, которые изменение добавляет (шаг 19).
Сбой: нет origin или ошибка клона → `WorkspaceError`, строка в Problems (шаг 24).
Checkout владельца не пишется никогда.
Проверка CI (origin на GitHub): у первого упавшего check run на HEAD клона аннотация «spending limit» → репо попадает в строку billing в дайджесте (GitHub не запустил CI, единственная проверка — гейт greenkeep); ошибка gh → ничего.
Module: `workspace`, `config`, `github`

### 9. Откаты

Решает: не пропустил ли гейт что-то неверное.
Ветки:
- коммит в базовой ветке говорит «This reverts commit <sha>» про записанное слияние greenkeep → статус `reverted`, `AutoPause`;
- слияние без сохранённого sha (push) → сначала спросить у GitHub.
Dry run: в состоянии в памяти слияний нет, проверка не срабатывает.
Module: `reverts`, `state`, `github`

### 10. Базовые тесты

Решает: можно ли работать с репо и с каким покрытием сравнивает каждый гейт.
Вход: клон. Выход: `TestRun` (ok, JSON покрытия, вывод, no_tests).
Ветки:
- нет `pyproject.toml` → `WorkspaceError` (revival не сделан);
- `uv sync --all-extras --all-packages`; корень тестов со своим pyproject синхронизируется отдельно;
- набор упал (`Fatal Python error`, плавающий segfault в Qt-тестах) → ещё один прогон; в логе заголовок падения и кадры самого репо, без кадров библиотек;
- набор красный или висит 30 мин → «baseline tests are red», репо дальше не идёт (и Dependabot тоже);
- exit 5 (нет тестов) → зелёный; покрытие всё равно показывает неимпортированные модули с 0% (`--source=.`), отсюда находки `untested`.
Покрытие: `coverage run --source=. --omit=tests/*,.venv/*`, опции pytest-cov и xdist убраны из addopts репо.
Module: `run`, `workspace`

### 11. Находки

Решает: полный список проблем репо.
Вход: клон, базовые тесты. Выход: `Baseline` (тесты, отпечатки lint, упорядоченные находки).
В push сначала `gh label create greenkeep / needs-human --force` (падает, если origin не на GitHub).
Источники:
- ruff JSON по конфигу репо (+ правила буста); отпечаток `ruff:<code>:<path>:<хэш текста строки>`, без номера строки; одинаковые строки файла получают `#1`, `#2`… по порядку строк, первая — простой отпечаток; последняя строка диапазона ruff сохраняется (`end_line`);
- `untested`: модули < 50% покрытия с ≥ 5 операторов, если покрытие что-то измерило или тестов нет;
- `vuln`: `uv export` → `pip-audit`, только при отслеживаемом `uv.lock`; цель — минимальная версия, закрывающая все advisory с исправленным релизом, в своей линии по возможности; advisory без него — в сообщение («no fix yet»); в отпечатке id исправимых advisory;
- `outdated`: `uv tree --outdated --depth 1` + PyPI, новейший стабильный в том же мажоре (минор для 0.x), который разрешают спецификаторы `pyproject.toml` и членов его uv workspace (`==`-пин → находки нет); пропуск, если в `.github/dependabot.yml` (не `.yaml`) есть экосистема `uv`/`pip`;
- `ready`: в pyproject `description`/`readme`/`urls`, в README разделы установки и использования (блок кода, который импортирует или запускает пакет, кроме строк установки, считается использованием), бейдж CI.
Сбой: ошибка PyPI → нет цели, нет находки; провал `uv export`/`uv tree` или не-JSON от pip-audit → репо в Problems (ни фиксов, ни Dependabot).
Module: `run`, `core`, `findings`, `deps`, `ready`, `workspace`

### 12. Заметки владельцу

Решает: что сообщить владельцу один раз вместо находки.
Заметки: нет файла лицензии; нет `README.md`.
Ветки: push → один раз на заметку (метка `told:<repo>:<note>`, ставится до отправки дайджеста); dry run → каждый раз.
Module: `run`, `ready`

### 13. Порядок работы

Решает: какая находка первая.
По приоритету вида: безопасность (vuln) → баги lint (ruff S/F/B) и найденные охотой → untested → outdated → готовность → стиль lint. Внутри вида порядок стабилен; ruff заранее отсортирован: S, F, B, затем C/PLR, прочие, E, W.
Ранг берётся по всему буквенному префиксу: `SIM` не `S`.
Module: `kinds`, `findings`

### 14. Кандидаты

Решает: над чем репо может работать сейчас.
Остаются: статус `open` или новая; не vendored (папка vendor или `VENDORED.md` выше); `attemptable`:
- ruff: каждая строка от первой до последней строки находки проходит правило покрытия; для C901/PLR0912/PLR0915 последняя — конец функции (`ast`); в тестовых файлах всегда;
- untested: тестового файла по целевому пути ещё нет, в репо меньше 3 запаркованных находок `untested:` (`MAX_PARKED_TESTS`), модуль не импортирует клиент БД или брокера и пакет, который ставит только нетестовый optional extra ближайшего `pyproject.toml` (extra `dev`/`test` и группа `dev` считаются установленными);
- outdated: тесты есть и общее покрытие ≥ 60%;
- vuln, ready: всегда.
Отсечка: первые 10. Находки охоты (шаг 15) минуют и проверку, и отсечку.
Module: `run`, `kinds`, `gate`, `findings`

### 15. Охота на баги

Решает: искать ли баги и в каком модуле.
Ветки:
- кандидаты есть, `hunt` выключен или бюджет исчерпан → нет охоты;
- иначе крупнейший модуль с покрытием ≥ 50%, ≥ 5 операторов, не дважды пустой в нынешнем виде (метка `hunt:<repo>:<path>` = sha + счёт).
Hunter (`--model`, 5 мин) заявляет ≤ 3 бага в JSON; Skeptic (`--review-model`) оставляет то, что не опроверг; каждый оставшийся на реальной строке, проходящей правило покрытия, — находка `bug`.
Сбой: таймаут, ошибка CLI, нечитаемый JSON → предупреждение, находок нет, модуль не помечен; Claude недоступен (`llm.unavailable`) → наверх (шаг 24).
Module: `hunt`, `llm`, `run`

### 16. Бюджет

Решает: можно ли работать над кандидатом сегодня.
Ветки: `vuln` → всегда; иначе `merged_today` (все репо, местный день) `< budget`; сверх → пропуск, репо может попасть в «waiting for budget».
Module: `run`, `kinds`, `state`

### 17. Issue плана

Решает: публичную запись о находке.
Ветки: push и issue нет в состоянии → `gh issue create` с меткой `greenkeep`; иначе тот же; dry run → нет.
Закрытие (push, сразу после baseline, до фильтра cool-down): открытая или запаркованная находка с issue, которой нет ни в baseline, ни в lint с правилами буста → `gh issue close` с комментарием, issue стирается из состояния. Не закрываются: `bug:` (в baseline их не бывает); `untested:`, если покрытие не измерено; `vuln:`/`outdated:`, пока у того же пакета нет новой находки (упавший pip-audit или PyPI не находит ничего). Иначе issue закрывает «Closes #N» смёрженного PR.
Затем запаркованная находка `untested:`, чей issue ждёт дольше 14 дней (`PARKED_TEST_DAYS`) → `gh issue close` с комментарием, issue стирается, находка остаётся запаркованной: две трети бэклога `needs-human` были запаркованными тестами.
Module: `run`, `github`, `state`

### 18. Изменение

Решает: изменение одной попытки, после `git reset --hard` + `clean -fdx` (`.env`, `.venv` сохраняются).
Ветки по виду:
- ruff с безопасным фиксом, первая попытка в этом прогоне → `ruff --fix --select <rule>` по файлу (все вхождения правила), затем новый исправимый lint от этого фикса; без LLM;
- ruff иначе → Claude (`FIX_SYSTEM`, файл или ±40 строк вокруг) → SEARCH/REPLACE по отслеживаемым файлам;
- untested → Claude (`TEST_SYSTEM`, модуль, связанные тесты, conftest, настройки, бюджет строк × 0.85, файл прошлой попытки этого прогона) → один блок python → тестовый файл, затем безопасные фиксы репо и удаление неиспользуемых имён;
- bug → Claude (`BUG_SYSTEM`) → правка исходника + новый или дописанный тест;
- vuln/outdated → `uv lock --upgrade-package name==version`;
- ready → шаблон (readme-field, urls, ci-badge) или Claude (`READY_SYSTEM`).
Буст и трудное изменение (untested, bug, C901/PLR0912/PLR0915) → планировщик (Opus, effort high) пишет план до 25 строк; патчер получает его в конце задания; в PR `<model> + plan by <planner>`.
Повтор в прогоне: причина прошлого провала без значений `.env`, первая строка плюс последние 1500 символов, дописывается в задание. Новый прогон начинает без неё.
Сбой: нет блоков, SEARCH не уникален, файл не отслеживается → `EditError` (попытка).
Module: `kinds`, `llm`, `edits`, `deps`, `ready`, `workspace`

### 19. Гейт

Решает: можно ли слить без человека.
Проверки по порядку:
1. что-то изменилось;
2. рамки вида: lint → только свой файл, изменённые строки покрыты до изменения, копий его строки ruff видит меньше, чем в базе; untested → только тестовые файлы в пределах бюджета строк; bug → свой файл + только добавленные строки тестов, строки исходника покрыты, каждый новый тест падает без фикса (exit 1); dependency → только `uv.lock`; ready → только свой файл и поле `[project]`, проверка проходит;
3. не добавлены `noqa`, `type: ignore`, `pragma: no cover`, `ruff:`, `pylint: disable`;
4. нет находки ruff с отпечатком, которого не было в базе (правила буста тоже; файл, который изменение добавляет, — только по правилам репо);
5. весь набор зелёный (`uv run`; виды зависимостей после `uv lock` делают `uv sync --all-extras --all-packages`, иначе `uv run` оставит пакет, нужный только extra, на старой версии), и не «нет тестов», если в базе тесты были;
6. untested → покрытие модуля выросло.
Сбой: `GateFailure` с причиной (попытка).
Module: `run`, `gate`, `kinds`, `workspace`

### 20. Ревью

Решает: последнее слово по изменению LLM.
Ветки: детерминированное изменение (ruff --fix, uv lock, шаблон) → без ревью; иначе `--review-model`, effort high, 15 мин, в клоне с применённым изменением.
Закрыто по умолчанию: всё, кроме `{"approve": true}`, → `GateFailure("reviewer rejected …")`.
Module: `run`, `llm`

### 21. Посадка

Решает: как изменение попадает в базовую ветку.
Коммит в `greenkeep/<sha1(отпечатка)[:10]>`: `<type>: <title>` ≤ 72 символов, тело: находка, модель, ревьюер, условия гейта, `Closes #N`. Заголовок PR — заголовок находки.
Ветки:
- push → force-push, открытый PR этой ветки или новый, `gh pr merge --squash --delete-branch`; отказ → опрос `mergeStateStatus`, пока UNKNOWN (10 × 3 с); BLOCKED → `gh pr checks --watch --required --fail-fast` (30 мин), повтор каждые 3 с (10 раз), пока gh отвечает «no required checks reported» (проверки ruleset появляются через секунды после PR); затем ещё один merge; снова отказ, но `gh pr view` говорит MERGED → слито;
- dry run → только локальный коммит, diff в лог.
Состояние: `merged`, PR, sha слияния. Одно слияние на репо за прогон: база после него устарела.
Сбой: слияние всё ещё отклонено (конфликт, отстала, нужен review, красный CI) или ошибка gh/git → попытка, изменение делается заново; `ValueError` из вывода gh → уровень прогона (шаг 24), ничего не засчитано.
Module: `run`, `github`, `state`

### 22. Провал

Решает: чего стоит неудачная попытка.
Ветки:
- Claude недоступен (`llm.unavailable`: `UsageLimitError`, `NotLoggedInError` или ошибка Claude с 5xx API, перегрузкой или сбоем соединения) → не считается, наверх (шаг 24);
- прочие ошибки Claude (таймаут, 4xx API вроде «prompt is too long», нечитаемый ответ) → считаются как плохое изменение;
- засчитано: attempts + 1, следующая попытка сразу; виды зависимостей паркуются сразу (`retries = False`); остальные на 3-й;
- запаркована → «Needs you» в дайджесте, комментарий в issue с одной строкой причины, метка `needs-human`;
- таймаут → засчитан, находка до следующего прогона, дальше следующий кандидат;
- 2 парковки в этом репо за этот прогон → cool-down 7 дней (шаг 7), находок больше нет; Dependabot всё равно идёт.
Module: `run`, `state`, `github`

### 23. Dependabot

Решает: какие открытые PR Dependabot greenkeep сливает за владельца.
После своей работы в репо, только на зелёной базе, только для origin на GitHub.
Ветки по PR:
- конфликт или красный на этом head раньше (метка `dependabot:<repo>:<n>`) → пропуск;
- любое `from X to Y` вне `<details>` не в своём мажоре (минор для 0.x) или ни одного → владельцу;
- только файлы `.github/` → слить по зелёным проверкам CI; проверок нет → ждать;
- иначе, до 3 за прогон → checkout head PR, sync, весь набор; зелёный → слить с `--match-head-commit`; красный → пометить head.
Отказ в слиянии ждёт обязательных проверок до 30 мин; провал метки не оставляет, PR тестируется снова в следующий прогон.
Dry run: «would merge» в лог, тесты не гоняются. Без бюджета, находок и issue.
Module: `dependabot`, `deps`, `github`

### 24. Остановки прогона

Решает: что исключение одного репо делает с остальными.
Ветки:
- `AutoPause` → записать PAUSE (push), строка в дайджест, стоп; день всё равно отмечается;
- Claude недоступен (шаг 22) → строка «Claude unavailable at <repo>, run stopped: <причина>», `limited`, стоп; дайджест уходит, день не отмечается, следующий часовой прогон пробует снова (и тоже шлёт дайджест);
- прочее → traceback в лог, первая строка в Problems, следующее репо.
Клон удаляется после каждого репо, если нет `--keep`.
Module: `cli`, `run`, `reverts`

### 25. Дайджест

Решает: что услышит владелец и считается ли день сделанным.
Текст: счётчики, Merged (свои и Dependabot), Needs you (парковки + заметки владельцу), Problems (и одна строка с репо, где GitHub не запустил CI из-за billing), Quiet (чистые, ждут бюджет, в cool-down), остаток бюджета.
Ветки:
- push → Telegram при `GREENKEEP_TG_BOT_TOKEN`/`CHAT_ID`, иначе уведомление на рабочем столе только с первой строкой; плановый, не `limited` и хотя бы одно репо склонировано (или репо нет) → метка `run` = день начала прогона;
- dry run → только лог.
Прогон, который не склонировал ни одного репо (нет сети после загрузки или сна), не отмечает день: следующий часовой пробует снова.
Module: `digest`, `cli`, `state`

### Результат

GitHub: issue плана, squash-слитые fix PR, слитые PR Dependabot, метки `needs-human`.
`~/.local/share/greenkeep/state.db`: строки `finding` (статус open/merged/parked/reverted, попытки, issue, PR, sha) и `mark` (run, cool-down, hunt, told, dependabot).
`~/.local/state/greenkeep/greenkeep.log`: история INFO и полные провалы и планы в DEBUG, 5 МБ × 4 файла.
Module: `state`, `digest`, `cli`

## Побочные потоки

### Дашборд

`greenkeep-ui` на 127.0.0.1:8095 (или следующий свободный порт; перезапускает работающий или открывает его в браузере).
Открывает state.db на запись (схема и миграции); раз в 30 с читает его и хвост лога; «Resume» удаляет PAUSE; «Dry run now» запускает `greenkeep` с живым логом; «Run with options…» открывает форму со всеми опциями CLI (репо, push, бюджет, модели, keep) и запускает ту же команду, при push сначала спрашивая подтверждение. Очередь прогонов полна (20) → уведомление вместо запуска; остановка дашборда убивает незавершённый прогон.
Показывает бюджет текущего момента (с бустом) и пишет, что таймер срабатывает каждый час, а прогон — раз в день.
Питает: шаг 1 (resume), вход dry run.
Module: `ui`, `port`
